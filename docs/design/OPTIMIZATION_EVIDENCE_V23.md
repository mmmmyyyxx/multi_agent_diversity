# Unified Team Prompt Search V2.3: optimization evidence

This sole active revision defines Gradient evidence, local evaluation and edit Memory.
It uses the existing production orchestrator, providers and two-level search. It
requires `MATH_OPTIMIZATION_EVIDENCE_BINDING_V1` and a fresh attempt, source,
authorization, cache namespace, prompt artifact and accounting freeze. V2.2
bindings and historical reports retain their exact meanings. Preparation is not
permission to call a provider.

## Evidence and hypotheses

The Solver retains V6 ordinary visible solutions, final-payload-only scoring,
qwen3-8b non-thinking and the frozen decoding/recovery policies. Its request
contains only its standalone procedure, public problem and immutable interface.
Only Optimize examples supply separately labeled dataset worked solutions to
one independent Gradient diagnostic per wrong example. The diagnostic records
observed failure, uncertain diagnosis, reusable correction and expected effect.
`UNCERTAIN` is an accepted outcome with no correction, not a retry trigger.
Only actionable corrections enter semantic clustering and the unchanged Pattern
responsibility selection. All-uncertain opportunities produce no candidate.
Worked solutions and ordinary response feedback are bounded at 4096 Unicode
characters with explicit truncation; original data/responses stay private.

The selected Pattern is a hypothesis. Layer1 may return `PROPOSE_EDIT` or
`NO_SAFE_EDIT`. The latter is neither improvement nor an unchanged deployable
candidate. Layer2 keeps WHO, allocation, team state, Pattern responsibility and
transition authority; these are not supplied to the mutation provider. Layer1
receives its current procedure, three mutation observations, one selected
hypothesis and bounded member-private Memory.

## Internal Optimize evaluation

Each opportunity deterministically freezes three Mutation, three SearchValidation
and three TeamProbe IDs. All three memberships are pairwise disjoint. Mutation
uses up to two selected-support wrong examples and correct preservation examples.
SearchValidation reserves one remaining selected-support wrong example when
available, otherwise a separately labeled other-current-wrong check, plus two
current correct examples. TeamProbe uses a further wrong example and two further
correct examples. Insufficient legal rows fail closed; no held-out backfill exists.
Before any Gradient call, opportunity feasibility requires at least four current
wrong and six current correct examples, enough legal capacity even for singleton
selected support. Insufficient pools produce `NO_FEASIBLE_OPPORTUNITY`, not a
post-spending role-construction failure. These technical bounds enter the policy
and do not gate admission of any generated, contract-valid candidate.

Current-correct IDs are shuffled by seed/member and rotated two positions per
member opportunity. This samples without replacement within each rotating pool,
returns to the pool after a cycle and updates the pool from committed profiles.
At wrap boundaries or with small/changing pools some adjacent overlap can occur;
it is recorded rather than claiming independent draws. Reliable source type/level
metadata is private audit context; no operation taxonomy is invented.

Parent and child use identical frozen local memberships. Validation observations
are measured after generation. They enter ranking and scope-labeled Memory;
only prior measurement counts may affect later mutation iterations, without
supplying validation questions/answers. A local parent advances on positive
validation gain with no broken validation-correct examples. Export ranks all
admissible evaluated candidates by validation net gain, validation loss,
mutation net gain, generation. No local acceptance veto gates outer admission.

The cap is derived as `(3+3) parent + 6*(3+3) children = 42` logical evaluations.
Six proposal generations, four exports and two Full promotions remain fixed.
Probe's cap becomes `4*3=12`, Full remains `2*60=120`, and the preexisting
Shadow cap is unchanged. A fresh resource derivation uses these exact roles and
one Gradient diagnostic per wrong example. Transport and Solver recovery stay
separately bounded. Full covers all Optimize and retains the V3 initial floor,
nonregressing Vote, target-or-team progress, fixed peers and equal plurality.
These Optimize roles provide internal transfer checks, not held-out generalization.

## Measured edit Memory

Before the first opportunity, existing initial Optimize profiles populate five
member-private competence records without any LLM or Solver calls. They bind
member, prompt, evaluation identity, correct/incorrect/invalid coverage and source
metadata. Original, current committed, newly fixed and newly broken coverage are
distinct; candidate-only gains never update committed coverage.

Every contract-valid evaluated edit stores actual parent/child prompt hashes,
opportunity, Pattern and support, hypothesis, intended edit, deterministic
lossless character-span diff, expected behavior, root and actual-parent local
effects, Probe/Full effects when measured, status and provenance. The diff is
derived from bytes/text, never from generated `change_summary`. Compound edits
are not attributed to individual clauses or latent causes.

`PROPOSED`, `LOCALLY_SUPPORTED`, `FULL_SUPPORTED`, `FULL_REFUTED`, `INCONCLUSIVE`
and `COMMITTED` are scope-specific candidate states. `FULL_REFUTED` means the
measured candidate failed the existing Full safeguards; it does not establish
that its general hypothesis is false. Capacity losers retain their measured local
scope without invented Full evidence. Operational failures and incomplete
opportunities do not produce a scientific Full status.

The existing private storage limit (24/member), Full-refuted failure cap (5/member), retrieval top-k (3), shared risk
storage/promotion policy and 1200-character context ceiling remain. Retrieval
prefers the same member, same Pattern/hypothesis and Full-refuted risks, then
recency; compact counts and deterministic action labels expose benefits/damage.
Private raw diffs, examples, worked solutions, answers and trajectories never
enter shared risk or Solver requests. Committed competence updates are prepared
and validated with the existing Memory transaction, then applied after commit.

## Executability and limits

The existing immutable interface and semantic contract checks are complemented
by bounded checks for optimizer-only field dependencies, ground-truth lookup,
example-answer lookup and copied long private solution/response fragments.
Generic exact-form, domain, sign, unit and substitution instructions remain legal.
Lexical checks are not comprehensive semantic verification. No critic, planner,
LLM Memory summarizer, prompt AST, extra controller or API guard agent is added.
Synthetic conformance cannot establish real optimizer diagnostic quality,
Solver stability, efficacy or generalization. Fresh V6 real-model baselines
must be measured; historical 22/60 cannot serve as the V6 baseline.

An explicitly frozen [initial prefix reconstruction](V23_PARALLEL_CAPACITY_REUSE_V1.md)
may combine verified prior V6 physical realizations with newly measured capacity
recovery draws. This requires its own policy, source manifest and authorization;
it is not a resumed experiment. Recompute initial competence from the complete
reconstructed profiles and disclose the historical/new realization mix.
