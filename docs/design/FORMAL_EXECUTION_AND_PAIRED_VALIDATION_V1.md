# Formal execution and paired Validation V1

This engineering extension retains Unified Team Prompt Search V2.5 Diagnostic
Limits 400, all generation parameters, repair and leakage guards, Layer1,
Full/Shadow admission, Memory, aggregation and `team_epoch_no_commit_v1`.
It grants no API or data authorization. Historical experiments retain their
original source, execution policy, results and classification.

## Execution physics

`STRUCTURED_INDEPENDENT_GRADIENT_EXECUTION_V3` freezes Solver concurrency eight
and optimizer concurrency two. Only independent per-example Gradient diagnoses
overlap. Each example retains the same packet and up to three sequential draws.
Worker-owned counters and responses are merged in wrong-universe input order;
numeric-guard writes are serialized. A fatal failure stops dispatch and drains
issued work before accounting can close. Clustering waits for every Gradient
worker. Reflection generations, local evaluated-parent updates, opportunities,
Full selection, Shadow and deployment remain serial. Five member realization
lanes and exact within-attempt fixed-peer cache semantics are unchanged.

The execution policy enters every role's request identity, manifest, startup
scope and source closure. This is engineering scheduling, not a claim that
stochastic real-provider outputs reproduce serial outputs. Provider throughput,
rate limits and real reliability require the newly authorized Canary. Concurrency
is not adapted after observing outcomes or silently reduced after a failure.

## Experiment resource boundary

The formal phase uses `MATH_FORMAL_SEARCH_RESOURCE_BOUND_V1`: at most fifty
optimization opportunities and thirty million charged Token, with the unchanged
scientific stopper and patience two. Neither ceiling guarantees saturation.
Resource truncation and engineering abort are separate from scientific completion.
The current production entrypoint and composition own this phase; no alternate
algorithm or compatibility controller is introduced.

`MATH_FORMAL_FULL_OPTIMIZE_METADATA_MEMBERSHIP_V1` selects all 150 Optimize records
and forty Shadow records by the existing subject/level proportional metadata
selector with a frozen seed. It changes no canonical split. Optimize and Shadow
are development evidence, including previously used development questions.
Initial competence is the aggregate initial correct count over the same complete
150-record Optimize support used for Full, not a per-question or validity floor.

The preserved `operational_pilot` storage key carries the versioned resource
bound in shared accounting physics; the formal phase is reported as formal,
never as another five-opportunity Pilot. The initial-profile and first-opportunity
owner reviews verify integrity and interfaces, with no efficacy-based veto.

`INTEGRITY_COMPLETE_CANARY_TO_FROZEN_FORMAL_V1` binds the preceding Canary's fresh
binding and attempt. Formal execution verifies its source, startup scope, terminal
inventory, complete initial profile, reached review milestones and closed ledger.
One complete production opportunity, or a legitimate no-repair terminal path,
can pass. Unreached branches stay explicitly unobserved; deterministic offline
smokes cover them. No positive Vote delta, Commit, actionable Gradient or forced
candidate is required. Canary truncation or engineering failure blocks progression.
The formal method, seed, memberships, baseline and budgets freeze before Canary
outcomes, and its five initial Arm B prompts and cache remain fresh.

## Monetary control

`USER_SELECTED_TOKEN_ONLY_RESOURCE_CONTROL_V1` is a separately frozen,
explicitly user-selected resource mode. It retains every phase's hard Token
ceiling, pre-transport reservations, conservative missing-usage charges,
role/model audit and independent journals. It reports no price or monetary cap.
The explicit `token_reporting_policy` enters binding reconstruction, manifest,
startup scope, every role's request identity and the separate Validation scope.
It is mutually exclusive with tariff accounting; missing both is not permission
to execute a new parallel or formal scope. Historical priced/draft evidence keeps
its original source identity. This mode changes no scientific or generation rule.

`ROLE_ROUTED_SUPPLIER_COST_RESERVATION_V1` requires supplied OpenLux and lwj
tariffs in one declared currency, input/output prices per million Token and any
physical-request fee. Model-vendor prices are not substituted for reseller prices.
Integer millionths of the currency represent amounts; reservations round upward.
Every physical attempt, including a failed transport, reserves its conservative
input bound, frozen output ceiling and request fee before dispatch. No cache
discount is assumed. Reliable usage reconciles the reservation; missing usage or
unresolved crash reservations charge the full bound. The hash-chained Token
journal owns both monetary and Token reservations, including concurrent in-flight
requests. Tariff/ceiling changes cannot reopen an existing journal.

The charged amount is conservative accounting under the supplied tariff, not an
invoice or proof of undocumented upstream billing. Unexpected usage remains fatal.
In tariff mode, prices, currency and separate phase hard limits enter startup
authorization and request identity. New parallel Canary and formal attempts must
freeze one explicit resource mode. `COST_CEILING` is resource truncation, never
scientific saturation.

## Post-search evidence boundary

`CURRENT_PAIRED_VALIDATION_300_V1` is a distinct, fresh, single-use authorization
and cache namespace with a six-million-Token ceiling and the explicitly frozen
resource mode (its own monetary cap when tariff accounting is selected).
It is part of the same formal experiment, not a new search or method selection.
Source and split metadata freeze with search. The phase cannot open any Validation
content until exact authorization and a verified search closure seal the frozen
initial team and last committed final team. A valid resource-truncated search may
be evaluated; its lack of scientific completion remains explicit. An engineering
abort cannot proceed. Test stays sealed.

Search reader and broker APIs continue to reject Validation/Test. A separately
checked Validation capability opens only the three hundred frozen Validation
records; a Validation-only broker admits Solver/Validation and rejects every
optimizer role, Optimize, Shadow and Test. No orchestrator or optimizer receives
held-out observations and the closed search cannot resume. The paired teams use
the same model, five member slots, generation, parser, aggregation and support.
An identical prompt/problem/member-slot request shares its provider realization
within this new evaluation attempt. Different slots remain independent even when
prompts are identical. Unchanged paired teams therefore yield identical evidence.

The primary endpoint is final-minus-initial Validation Vote accuracy. Oracle
coverage, member correctness and validity are separate secondary measurements.
The experiment-specific analysis reports paired gains/losses, a two-sided exact
McNemar/binomial p-value and a paired example bootstrap interval (10,000 draws,
seed 86, 95%, interpolated empirical quantiles). No partial, cost-censored
Validation support is scored: truncation/abort is `NOT_EVALUABLE`, with receipts
preserved and no unauthorized retry. These settings are not global scientific
rules or a new stopping criterion.

A fixed unoptimized Arm B team is an inference-matched baseline, not a
training-compute-matched optimization control. One optimized team/seed can test
paired held-out team performance but cannot establish seed robustness, benchmark
generality or causal effects of Responsibility, Pattern or Memory. Their observed
trajectories support mechanism hypotheses only. Oracle-to-Vote conversion remains
a research question; this extension adds no conversion mechanism or new gate.
