# Structural candidate contract V2

This user-requested scientific amendment replaces the current candidate Guard;
there is no selectable old candidate Guard or semantic-filter compatibility mode.
Identity: `STRUCTURAL_SINGLE_BLOCK_CANDIDATE_CONTRACT_V2`.
The count-responsibility method family, diagnosis universe, Pattern selection,
Memory behavior, population size, aggregation and performance admission remain.
Every new run must freeze the revised candidate identity, policy, source and wire.
Existing experiments and their manifests, authorizations, prompts and outcomes
remain immutable and require their original Git source for historical execution.

## Candidate boundary

- State remains exactly Role, Strategy and Answer, each a nonempty string.
- A proposal names one of those blocks and supplies one nonempty replacement.
  Other blocks retain their exact bytes. Multiple block replacements are invalid.
- No character cap, block budget, append-only restriction, keyword semantics,
  example/solution overlap rule, fixed-answer rule, peer-copy rule or repeated
  candidate rejection determines legality. Useful training content may be learned.
- Identical parent bytes produce a recorded `NO_OP` / `SKIPPED_NO_OP`, consume the
  ordinary opportunity/slot, skip candidate measurement and stop generation for
  that opportunity/slot. They do not force retries or count as malformed output.
  The single-Prompt kernel still completes 20 opportunities without efficacy stops.
- Malformed proposals use the existing bounded format retries. JSON duplicate
  keys, conflicting/multiple objects, missing/invalid block names, nonstring/empty
  content and explicitly incomplete output remain format failures.
- Parsing accepts the two current single-block JSON envelopes, an unambiguous
  complete outer JSON fence, or one complete object surrounded by prose. It never
  invents truncated content or rewrites invalid mathematical JSON escapes.
  Summary metadata has no arbitrary character cap and may be absent.

`SystemPrompt`, shared candidate legality, team Reflection, independent module
generation, the older single-Prompt generation helpers and telemetry all use the
new boundary. Root/peer duplicates are not text violations. Existing exact-request
Solver caches and downstream population identity handling still apply.
Group narrative validation is a separate diagnostic-source function with its
existing behavior preserved, not an alternate candidate Guard. Its source-aware
abstraction, typed support membership, correctness provenance, field schema and
diagnostic resource policy remain. Candidate generation never calls that function.
Gradient/Pattern diagnostic contracts and Memory delivery budgets are not Prompt
candidate length limits and are unchanged. Historical flat-text GEPA adapters and
their audit utilities are outside the current structured production graph; they
cannot supply the old Guard to the new current or independent candidate pipeline.

## Unchanged measurement and isolation

The single-Prompt kernel retains one generated proposal per opportunity,20
opportunities and strictly more correct Validation100 answers than the retained
Prompt (at least one extra correct). No-op is a separate skipped category, not
Validation rejection or format exhaustion. The old Prompt and recorded profiles
are retained on skips/rejection. Team Full/Shadow/Vote/fitness admission is unchanged;
no GEPA Pareto selection or minibatch acceptance algorithm is added.

Solver messages remain exactly the rendered Prompt and raw problem. No Optimizer,
reference, Gradient, Pattern, team or Memory channel is added at inference. Content
mentioning such terms is permitted but does not create access to those objects.
Optimize/adaptive Validation/sealed Test memberships and access capabilities remain.

Physical completion-token ceilings, explicit truncation reporting, actual provider
request/context feasibility, durable accounting and authorization remain technical
execution constraints. They do not bound candidate characters. Existing request
capacity checks reserve output space and conservatively account for the serialized
request; this amendment does not guess new model context sizes or change models,
SDK, generation capacities, semantic retry counts or data memberships. Provider
capacity failures must stay explicit, never disguised as a semantic rejection.

## Official GEPA reference and scope

Reviewed 2026-10-15: official
[proposal parsing](https://github.com/gepa-ai/gepa/blob/main/src/gepa/strategies/instruction_proposal.py)
and [reflective mutation](https://github.com/gepa-ai/gepa/blob/main/src/gepa/proposer/reflective_mutation/reflective_mutation.py).
GEPA accepts fenced/unfenced proposal text and skips empty text-update proposals.
This project retains its explicit three-block interface, adds deterministic JSON
wrapper recovery, and explicitly skips byte-identical proposals as requested by
the user. It does not claim identical parsing or selection to every GEPA version.

The default independent draft is schema V5/kernel V5 and is preparation-only.
The formal preparation pointer names the fresh structural-candidate DRAFT;
an appended manifest schema branch binds the new policy while preserving every
historical schema branch. It grants no API or data access authorization. Old
single-Prompt documents are validated as exact published Git metadata, never
regenerated from the changed current runtime. Metadata validation grants no
execution eligibility. A new run needs fresh registration, freeze and authorization.

## Offline evidence requirements

Compare all493 sealed historical draws against the new contract without running
Solver/Validation. Bind every original response and parent to the historical
receipt and index hashes. Report eligible/no-op/format-rejected counts and old
reason transitions, specifically the10 confirmed old false rejections. Reclassification
is per recorded draw; new no-ops would end historical retry chains, so totals are
not a counterfactual execution, measured gain, historical acceptance or rerun.
Verify long prompts, malformed/ambiguous formats, single-block edits, actual Solver
input isolation, no-op evaluation counts, strict Validation and team admission.
